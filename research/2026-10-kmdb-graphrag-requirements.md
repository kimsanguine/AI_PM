# KMDb 한국영화 GraphRAG 과제 — 개발요건서

> 한 줄 정의: 한국영상자료원 KMDb 영화 데이터로 지식그래프를 두 번 만든다. 한 번은 구조화 필드로(정답), 한 번은 줄거리·수상·키워드 텍스트에서 LLM으로 추출해서(평가 대상). 두 그래프의 차이로 추출 정확도를 재고, 정답 그래프에서 자동 생성한 멀티홉 질문 100개로 Naive RAG 대 GraphRAG를 비교한다.
>
> 설계 원칙: Neo4j 영화 데모의 반대 축. 데모는 완성된 그래프 위에 벡터 검색을 얹고 평가가 없다. 이 과제는 그래프를 만드는 과정을 측정하고, 질의 결과를 수치로 남긴다.

---

## 1. 배경과 목표

### 1.1 왜 이 과제인가

| 근거 | 내용 |
|---|---|
| 채용 연결 | 채용 리서치에서 GraphRAG(스카이월드와이드, 메타펫), 추천·검색(카카오 Agentic Search, SOOP 개인화 추천), 평가 파이프라인(네이버 필수) 요건 확인 |
| 정답 라벨 비용 0 | KMDb 구조화 필드(스태프·역할·수상·제작사)가 그대로 정답 그래프가 된다. DART의 XBRL과 같은 구조 |
| 시장 공백 | GraphRAG 표준 벤치마크가 없고 결과가 평가 방식에 따라 뒤집힌다. 한국어 데이터 벤치마크는 없다 |
| 학습 동기 | 영화는 누구나 질문을 떠올릴 수 있는 도메인이다. 멀티홉 질문이 자연스럽다 |

### 1.2 목표 지표

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 관계 추출 F1 | 0.7 이상 | LLM 추출 그래프 vs 구조화 정답 그래프 |
| 멀티홉 정답률 | Naive RAG 대비 +15%p | 자동 생성 질문 100문항 |
| 응답 지연 | p95 5초 이하 | 트레이스 |
| 질문당 비용 | 측정·보고 | 토큰 로그 |

목표치는 가설이다. 베이스라인 측정 후 1주차 말에 재설정한다.

### 1.3 범위 밖

- 영화 추천 UI. 결과는 API와 간단한 데모 페이지까지만
- 외국영화. 한국영화 또는 한국 제작 참여작으로 한정
- 리뷰·평점 데이터. NSMC는 영화 제목 필드가 없어 연결 불가
- KOBIS 데이터와의 결합. 약관의 "결과를 다른 정보와 혼합하지 않고 독립 노출" 조항 해석이 확인될 때까지 보류

## 2. 데이터 요건

### 2.1 데이터 출처

| 출처 | 용도 | 접근 조건 | 상태 |
|---|---|---|---|
| KMDb 영화 상세정보 API | 그래프 본체, 텍스트 원문 | 회원가입 → 개발계정 신청 → 심의 후 서비스키. 개발계정 일 1,000건. 공공누리 OPEN, "누구나 자유롭게" | 필드 확인 완료 |
| KOBIS 박스오피스 API | (보류) 흥행 시계열 | 즉시 키 발급. 일일 한도 미확인. 출처 명시, 결과 혼합 금지 조항 | 약관 문의 전까지 제외 |

### 2.2 KMDb 필드 매핑

| 그래프 요소 | KMDb 필드 | 비고 |
|---|---|---|
| Movie 노드 | movieId, movieSeq, title, titleEng, prodYear, releaseDate, runtime, rating, nation, audiAcc, posterUrl, kmdbUrl | movieId+movieSeq가 고유키 |
| Movie.plot (텍스트) | plot | LLM 추출 입력 1 |
| Movie.keywords (텍스트) | keywords | LLM 추출 입력 2 |
| Movie.awards (텍스트) | Awards1, Awards2 | LLM 추출 입력 3. 수상명·연도·부문이 자유 텍스트 |
| Person 노드 | directorNm, directorId, actorNm, actorId, StaffNm, StaffId | StaffId가 있을 때만 동일인 병합. 없으면 이름+역할군으로 임시 키 |
| DIRECTED 관계 | directorNm → Movie | |
| ACTED_IN 관계 {role} | StaffNm + StaffRole(배역) | staffRoleGroup이 "출연"인 행 |
| WORKED_ON 관계 {credit} | StaffNm + staffRoleGroup(촬영, 편집, 음악 등) | |
| Company 노드, PRODUCED_BY | company | 문자열 분리 필요(복수 제작사) |
| Genre 노드, HAS_GENRE | genre | 쉼표 분리 |
| Keyword 노드, HAS_KEYWORD | keywords | 정답 그래프에서는 구조화 키워드로 사용. 추출 그래프에서는 LLM이 plot에서 뽑은 키워드와 비교 |
| Award 노드, WON {year, category} | Awards1, Awards2 파싱 | 정답 그래프용 규칙 파서를 먼저 만들고, 규칙 파서의 정확도를 50건 수동 검수로 확인 |

### 2.3 수집 규모와 한도 계산

| 항목 | 값 | 계산 |
|---|---|---|
| 대상 | 한국영화 2000년 이후 극장 개봉작 | createDts=2000, nation=대한민국, type=극영화 |
| 예상 건수 | 5,000~8,000편 | 확인 필요 (TotalCount로 1회 호출 시 확정) |
| 호출당 건수 | 최대 500 (listCount) | detail=Y에서도 500이 허용되는지 확인 필요 |
| 필요 호출 | 20회 내외 | 개발계정 일 1,000건 안에서 하루에 끝남 |
| 재수집 정책 | 원본 JSON을 디스크에 저장, API 재호출 금지 | 팀원이 각자 키를 받되 수집은 1인이 수행 |

### 2.4 데이터 품질 규칙

- 동일 인물 판별: StaffId 우선, 없으면 (이름, 역할군, 활동 연도 ±10년)으로 후보 병합 후 수동 검수 100건
- 제작사명 정규화: "㈜", "(주)", "주식회사" 제거 후 비교
- 수상 텍스트: 규칙 파서 → 실패 건은 LLM 보조 → 정답 그래프에는 규칙 파서 성공분만 포함(정답의 순도 유지)
- 결측: plot이 50자 미만인 영화는 추출 평가에서 제외하되 그래프에는 포함

## 3. 사용자 스토리

INVEST 원칙으로 쓴다. 각 스토리는 카드(제목), 대화(맥락), 확인(수용 기준)으로 구성한다.

### US-1. 인맥 질문에 답한다

- 카드: 영화 팬으로서, "봉준호와 함께 일한 촬영감독이 참여한 다른 감독의 영화 중 수상작"을 물으면 영화 목록과 근거 경로를 받고 싶다.
- 대화: 3홉 질문이다. 벡터 검색만으로는 못 푼다. 경로를 함께 보여줘야 신뢰할 수 있다.
- 확인: 정답 그래프에서 생성한 3홉 질문 30개 중 GraphRAG 정답률이 Naive RAG보다 높다. 응답에 노드 경로가 포함된다.

### US-2. 줄거리와 관계를 섞어 찾는다

- 카드: 영화 팬으로서, "계급 소재인데 코미디 톤이고 같은 제작사가 만든 영화"를 물으면 조건을 모두 만족하는 영화를 받고 싶다.
- 대화: 소재와 톤은 줄거리 텍스트(벡터), 제작사는 그래프 관계다. 둘을 합쳐야 한다.
- 확인: 하이브리드 검색이 벡터 단독, 그래프 단독보다 정답률이 높은 질문 유형이 최소 1개 있다. 없으면 그 사실을 보고한다.

### US-3. 텍스트에서 관계를 뽑는다

- 카드: 데이터 엔지니어로서, 줄거리·수상·키워드 텍스트만 주어졌을 때 인물·역할·수상 관계를 자동 추출하고 정확도를 알고 싶다.
- 대화: 실무에서는 구조화 필드가 없는 문서가 대부분이다. 이 과제에서는 정답이 있으니 추출기 품질을 잴 수 있다.
- 확인: 추출 그래프와 정답 그래프의 엔티티·관계 P/R/F1이 보고서에 있다. 관계 유형별로 분리돼 있다.

### US-4. 틀린 이유를 안다

- 카드: 심사위원으로서, 시스템이 틀린 질문 20개의 원인 분류(검색 실패, 추출 누락, 추론 오류, 질문 모호)를 보고 싶다.
- 대화: 점수보다 실패 분석이 면접에서 더 강하다.
- 확인: 실패 사례 20건이 4분류 중 하나로 라벨링돼 있고, 각 분류별 대응안이 한 줄씩 있다.

### US-5. 밖에서 쓴다

- 카드: 다른 팀 개발자로서, HTTP로 질문을 보내고 답과 근거 경로를 JSON으로 받고 싶다.
- 대화: 배포 URL과 트레이스가 포트폴리오의 증거다.
- 확인: 배포된 엔드포인트가 24시간 살아 있고, 모든 요청이 Langfuse에 트레이스로 남는다.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | KMDb API에서 대상 영화를 수집해 원본 JSON으로 저장한다 | 필수 |
| FR-2 | 구조화 필드로 정답 그래프(G-gold)를 Neo4j에 적재한다 | 필수 |
| FR-3 | plot, keywords, Awards 텍스트에서 LLM으로 트리플을 추출해 추출 그래프(G-llm)를 적재한다 | 필수 |
| FR-4 | G-llm과 G-gold를 엔티티·관계 단위로 비교해 P/R/F1을 계산한다 | 필수 |
| FR-5 | G-gold에서 Cypher 템플릿으로 멀티홉 질문·정답 쌍 100개를 생성한다 (1홉 30, 2홉 40, 3홉 30) | 필수 |
| FR-6 | Naive RAG: plot 임베딩 벡터 검색 + LLM 답변 | 필수 |
| FR-7 | GraphRAG: 자연어 → Cypher 변환 → 그래프 질의 → LLM 답변 | 필수 |
| FR-8 | Hybrid: 벡터 후보 → 그래프 확장 → 재순위 → 답변 | 필수 |
| FR-9 | LangGraph 에이전트가 질문 유형에 따라 FR-6~8 중 경로를 선택하고, 실패 시 재시도한다 | 권장 |
| FR-10 | FastAPI 엔드포인트 `/ask`가 답, 근거 경로, 사용 경로(naive/graph/hybrid), 지연, 토큰을 반환한다 | 필수 |
| FR-11 | 모든 요청을 Langfuse에 트레이스로 기록한다 | 필수 |
| FR-12 | 실패 사례 20건을 4분류로 라벨링한 보고서를 만든다 | 필수 |
| FR-13 | 간단한 데모 페이지(질문 입력, 답, 경로 시각화) | 선택 |

## 5. 비기능 요구사항

| 항목 | 요구 |
|---|---|
| 그래프 DB | Neo4j (AuraDB Free 또는 Docker). 벡터 인덱스는 Neo4j 내장 사용 |
| 오케스트레이션 | LangGraph. 상태 그래프에 경로 선택·재시도·HITL 노드 |
| 관측 | Langfuse 셀프호스트 또는 클라우드 무료 티어 |
| 배포 | FastAPI + Docker. 클라우드 1종(팀 선택) |
| 재현성 | 원본 JSON, 추출 프롬프트, Cypher 템플릿, 평가 스크립트를 저장소에 포함. 시드 고정 |
| 비용 상한 | 팀당 LLM 비용 상한을 정하고 질문당 비용을 보고 |
| 호출 예절 | KMDb 개발계정 일 1,000건 준수. 클라이언트 측 rate limiter. 원본 재호출 금지 |
| 출처 표시 | 데모·보고서에 "출처: 한국영상자료원 KMDb" 명시. 공공누리 유형 확인 후 표기 |
| 키 관리 | 서비스키는 환경변수. 저장소 커밋 금지. 팀원 간 공유 금지(API마다 1인 1키) |

## 6. 아키텍처

```
KMDb API ──(수집 1회)──▶ raw/*.json
                              │
            ┌─────────────────┴──────────────────┐
            ▼                                     ▼
   구조화 필드 적재                        텍스트 → LLM 트리플 추출
   (G-gold, Neo4j)                        (G-llm, Neo4j 별도 라벨)
            │                                     │
            │◀──────── FR-4 그래프 비교 ──────────┘
            │
   Cypher 템플릿 → QA 100문항 (gold)
            │
            ▼
   LangGraph 에이전트 ── naive / graph / hybrid 경로
            │
   FastAPI /ask ── Langfuse 트레이스
            │
   평가 스크립트 → 리더보드 + 실패 분석
```

G-gold와 G-llm은 같은 Neo4j 인스턴스에 라벨 접두사(`Gold:`, `Llm:`)로 분리한다. 질의 시스템은 기본으로 G-gold를 쓰고, 추가 실험으로 G-llm 위에서 같은 QA를 돌려 "추출 오류가 답변 정확도에 미치는 영향"을 잰다.

## 7. 평가 요건

### 7.1 그래프 구축 평가 (FR-4)

| 항목 | 정의 |
|---|---|
| 엔티티 매칭 | 이름 정규화 후 정확 일치. 별칭은 KMDb Id로 해소 |
| 관계 매칭 | (주어, 관계유형, 목적어) 삼중 일치. 속성(배역명)은 별도 점수 |
| 보고 단위 | 관계 유형별 P/R/F1. 전체 micro-F1 |
| 함정 | 수상 텍스트의 연도·부문 파싱. "남우조연상"과 "조연상(남)" 같은 표기 차이 |

### 7.2 질의 평가 (FR-5~8)

| 항목 | 정의 |
|---|---|
| 정답 형식 | 엔티티 집합. 순서 무관 |
| 지표 | 집합 F1, 완전 일치율. 홉 수별 분리 |
| 비교군 | naive, graph, hybrid 3개. 에이전트 자동 선택은 4번째 |
| 통제 | 같은 LLM, 같은 프롬프트 템플릿, 같은 top-k |
| LLM-as-judge | 쓰지 않는다. 정답이 구조화돼 있으므로 규칙 채점 |

### 7.3 심사 비중

| 산출물 | 비중 |
|---|---|
| 멀티홉 정답률과 베이스라인 대비 개선 | 30% |
| 관계 추출 F1과 유형별 분석 | 25% |
| 실패 분석 20건 | 20% |
| 배포 URL, 트레이스, 비용·지연 표 | 15% |
| 재현 가능한 코드와 README | 10% |

|---|---|---|---|
| 사전 1주 | D-14 ~ D-8 | 대상 영화 목록·movieId 공개, Cypher 질문 템플릿 공개, 평가 스크립트 공개 | KMDb 회원가입, 개발계정 신청(심의 기간 고려) |
| 사전 2주 | D-7 ~ D-1 | 샘플 100편으로 G-gold 예시 공개, 수상 텍스트 규칙 파서 공개 | 수집 완료, Neo4j 기동, 베이스라인(naive) 점수 제출 |
| 본선 1일차 | 오전 | | G-gold 적재, QA 100문항 생성, graph 경로 구현 |
| 본선 1일차 | 오후 | | LLM 추출 → G-llm, FR-4 점수 |
| 본선 2일차 | 오전 | | hybrid, 에이전트 경로 선택, 배포 |
| 본선 2일차 | 오후 | 리더보드 마감 | 실패 분석, 제출 |

KMDb 개발계정 심의 기간이 공개돼 있지 않다. 사전 1주 첫날에 신청하도록 공지하고, 주최 측은 예비로 원본 JSON을 보관한다(공공누리 OPEN이므로 재배포 가능 여부를 약관에서 최종 확인).

## 9. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| KMDb 심의 지연 | 참가자가 본선까지 키를 못 받음 | 주최 측 원본 JSON 예비 배포(약관 확인 후) |
| detail=Y에서 listCount 500 미허용 | 호출 수 증가 | 사전 1주에 1회 테스트로 확정. 미허용 시 100건 단위로 재계산 |
| 동일 인물 병합 오류 | 정답 그래프 오염 | StaffId 있는 관계만 정답에 포함. 나머지는 "미확정" 라벨 |
| 수상 텍스트 파싱 실패 | WON 관계 정답 부족 | 규칙 파서 성공분만 정답. 실패분은 추출 평가에서 제외 |
| Cypher 생성 환각 | graph 경로 정답률 저하 | 스키마를 프롬프트에 고정, 실행 전 구문 검증, 실패 시 재생성 1회 |
| KOBIS 약관 충돌 | 흥행 데이터 결합 불가 | 보류. 문의 결과에 따라 2회차에 추가 |
